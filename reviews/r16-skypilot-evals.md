1. **[P1] Container probe cannot read the private header — `infra/verda/eval.yaml:130`.** The mounted header is root-owned and mode 0600, while the pinned curl image runs as `curl_user` ([image build source](https://github.com/curl/curl-container/blob/8.10.1/create_appliance_image.sh#L35)). The probe therefore cannot authenticate, and `set -e` aborts before Harbor starts. Add `--user 0:0` to this probe, preserving the private file permissions.

2. **[P1] Orphans still have no backstop when the watcher crashes — `infra/verda/fh.py:896,1053–1055`.** After the immediate sweep, delayed instances depend entirely on a local `eval-wait` process. If it crashes, those instances never receive the job timeout or autodown configuration and can bill indefinitely. Reconciliation also stops after a window measured from launch start. Install durable, restartable reconciliation before provisioning, persist pending cleanup, and keep reconciling until deletion is confirmed; use an independent janitor or provider expiry for protection when the local machine disappears.

3. **[P1] `--new` can discard ownership of live orphans — `infra/verda/fh.py:850–854`.** A `launch_failed` box absent from SkyPilot passes this check even when Verda has booted its instance. Consequently, `--new --only 1` can forget an old box 2 permanently; subsequent sweeps only know the replacement fleet. Reconcile old boxes against Verda before replacement and retain their cleanup records until provider deletion is confirmed.

4. **[P2] Exhausted fetch retries still report success and delete results — `infra/verda/fh.py:1033–1042`.** After three retrieval failures, a `SUCCEEDED` job becomes `done` and is deleted despite never fetching successfully. I reproduced this with missing `box.json`: `fetched_at` remained absent, yet the message claimed successful retrieval and `eval-wait` would return success. Only mark `done` after a successful fetch. Exhausted retries must produce a distinct failure state and nonzero exit, with an accurate deletion/data-loss message.
